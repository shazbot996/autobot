# Changelog — autobot

This file records what changed in autobot between releases, for the people who use it. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

`CHANGELOG.md` is a **historical** Root document. It records what happened, and a released entry is never rewritten afterwards. For that reason CR2 does not offer `Revise` or `Answer questions` on this square. The log grows instead. New work is added under **Unreleased** as it lands. When you cut a release, those entries move under a new version heading, with the newest version first, grouped as Added, Changed, Deprecated, Removed, Fixed, and Security. A coding agent can add these entries during a build run, for example through `Direct`. You can also add them by hand.

Unlike the other starter documents, the entry below is not tutorial text to sweep away. It is the true first record of this project: the moment it was seeded.

## Unreleased

### Added

- Smart Start intake (2026-11-25) replaced the `cr2-empty` tutorial with autobot's first real context. Rung 0 rewrote `README.md`, `AGENTS.md`, and the Core documents `BRIEF.md`, `GLOSSARY.md`, `CONVENTIONS.md`, `CONSTRAINTS.md` (`CN-1`, `CN-2`: local-only speech-to-text, wake-word modeling and text-to-speech), `SCHEMA.md` and `ARCH.md`. Rung 1 added `docs/context/INFRASTRUCTURE.md` (Intel NUC, WSL test machine, `cambiumplatform.com` Google Cloud organization). Rung 2 added ADR 0001 (Python, proposed), ADR 0002 (Gemini ADK with locally persisted state, active) and ADR 0003 (faster-whisper and piper-tts, proposed). Rung 3 added stub specs `wake-word-listener-SPEC.md`, `rules-first-routing-SPEC.md` and `agent-sessions-SPEC.md`.
- Headless wake-word prototype (2026-11-25), built from `docs/plans/active/headless-wake-word-prototype-PLAN.md`. An always-on listener on the Intel NUC hears any utterance containing the wake phrase `autobot` and answers aloud, "Yes?". It reads the microphone at 16 kHz through PipeWire, drops silence with Silero VAD, and runs one detector per configured wake phrase behind a `Detector` protocol with two kinds: `openwakeword`, a model trained here for `autobot` by `make train-wakeword`, which is the configured kind, and `text_match`, which transcribes speech with faster-whisper and looks for the phrase. Each wake is published as a `WakeEvent` JSON line to `run/listener.log` and to the Unix socket `run/listener.sock`. The acknowledgement is synthesised locally with piper-tts. No audio leaves the machine and the listener makes no network calls.
- `Makefile` runtime control layer: a bare `make` prints every target; `setup`, `test`, `lint`, `typecheck`, `up`, `down`, `status`, `logs`, `audio-check`, `deploy`, `fetch-models` and `train-wakeword`, with `backend-up` and `backend-down` as aliases.
- The `openwakeword` engine (`src/autobot/listener/engines/openwakeword.py`). It runs openWakeWord's two feature models and the trained `autobot` model with `onnxruntime` alone, one thread each, about 1.5 ms per 80 ms frame; the `openwakeword` Python package is not a dependency, because it needs `tflite-runtime`, which has no wheel for Python 3.12. It fires when the score reaches the phrase's `threshold` and then ignores two seconds of audio. It is fed stretches of speech only, through a speech gate with wider margins than `text_match` uses (0.96 s before the speech, 0.8 s after), which a detector now asks for with a `gate_margins` attribute. In the same room over the same minutes the listener used 8.8 % of one core and 176 MiB with `openwakeword`, against 120.8 % and 341 MiB with `text_match`; in silence both use 4.7 %.
- `make train-wakeword` (`src/autobot/wakeword/`) trains the wake-word model on the NUC's CPU: speech synthesised with piper-tts in 20 voices (the phrase in carrier sentences, words that sound like it, ordinary speech), reverb and noise, openWakeWord features and its general negative features, a small classifier, and an evaluation on 7 voices kept out of training. It is resumable at every stage, and writes `models/wakeword/autobot.onnx` and `autobot.json` atomically, keeping the model it replaces. The first model, from a short run, hears 74 % of held-out `autobot` clips at threshold 0.9 and makes 3.9 false accepts per hour on openWakeWord's validation audio, which is not yet good enough for a house; fed through the listener's own frame path it detected 127 of 140 held-out utterances (90.7 %) and fired on 3 of 140 other sentences. A run with ten times the synthesised speech was started on 2026-11-25 to replace it.
- `make fetch-models` (`src/autobot/fetch_models.py`) downloads the published model files into `models/`, and with `TRAIN=1` the voices and data sets the training needs. It is the only code that downloads; the listener, the tests and the training do not.
- Terminal user interface, opened by `make deploy`: screens for audio devices and levels, the wake phrase, the listener's systemd unit and the host, with placeholders for cloud deployment and identity and access management.
- `config/autobot.toml`, the one configuration file, and `deploy/autobot-listener.service`, the systemd user unit that runs the listener from boot.
- `make audio-check`, which checks the NUC's microphone and speaker and refuses to run on any other machine.
- Tests (`pytest`), linting (`ruff`) and strict type checking (`mypy`), run from recorded audio fixtures with no microphone, speaker or network. The fixture tests pass for both detector kinds. The fixtures are placeholders synthesised with piper-tts until recordings are made on the NUC.
- ADR 0004, accepting Python (ADR 0001) and faster-whisper and piper-tts (ADR 0003) and naming `mypy` as the type checker, and ADR 0005, recording openWakeWord with a custom-trained `autobot` model as the wake-word engine, with `text_match` as the fallback kind.
- Wake-word training studio (2026-11-26), built from `docs/plans/active/wake-word-training-studio-PLAN.md` steps 1 to 12 against `docs/specs/active/autobot-wake-word-training-studio-SPEC.md`. The terminal user interface is now the application, and its first job is to take the listener from *untrained* to *installed* on the owner's own voice. It was checked on the NUC through pseudo-terminal runs with scratch data and a virtual audio source. It has not yet been used with a real voice: no session has been recorded and no model has been trained on real recordings.
- The voice dataset (`src/autobot/wakeword/dataset.py`): recordings under `data/voice/` with one manifest, `manifest.jsonl`, git-ignored and never leaving the NUC. A stable split holds out one script prompt in five (by a hash of speaker and prompt identifier), one unprompted clip in five (by file name) and the last fifth of every ambient recording.
- A scripted recording session (`src/autobot/wakeword/script.py`, `src/autobot/tui/session.py`): 56 prompts for the phrase (bare, "hey", "yo", in a sentence, slow, fast, quiet, raised, near, far), 20 sound-alikes, 10 ordinary sentences and five one-minute room recordings, with an optional sixty-minute room recording that can be ended after thirty. Every clip is labelled by the prompt that asked for it, and a session resumes at the first prompt not yet answered.
- Training on real recordings: `make train-wakeword` gained a `real` stage that cuts the training side of the dataset into windows beside the synthetic ones, with half of every batch of positives and a third of every batch of negatives real. The evaluation file gained a `real` section naming the clips and ambient slices trained on and held out.
- An evaluation on the held-out real recordings (`src/autobot/wakeword/evaluate.py`, also `python -m autobot.wakeword.evaluate MODEL`): recall, false accepts on negatives and false accepts in ambient audio per threshold, with the counts and minutes they rest on. False accepts per hour is a rate only from twelve minutes of held-out ambient, and a count below that.
- Candidate, install and revert (`src/autobot/wakeword/install.py`, the Candidate screen): the candidate is compared with the installed model on the same held-out recordings, with a verdict only from twenty positives, twenty negatives and twelve ambient minutes and a tolerance of one clip or event. An install keeps the model it replaces as `autobot.prev.onnx` and writes `kind`, `model` and `threshold` to `config/autobot.toml`; the threshold is the one the screen recommended on the held-out set as it is now (the evaluation file's when nothing is held out), it is recorded in the installed evaluation as `installed_threshold` when it differs from the file's, and a revert restores it. A model file the configuration does not name as `openwakeword` is a leftover: kept, not counted as installed, not compared.
- The listener publishes a `score` event for every stretch of speech, to `run/listener.sock` only and before any wake the stretch causes, with a stretch identifier that starts at 1 with each run. It holds the last five stretches with their pre-roll (at most the last 30 s of each) and the last ten seconds of microphone audio in memory, and `python -m autobot.listener.control snapshot --stretch ID` or `--buffer` has it write one to `run/snapshot.wav`. It writes nothing of them otherwise.
- A Live monitor screen that shows scores and wakes as they happen and saves a marked utterance (right, wrong, missed) into the dataset with `source = "monitor"`, and a Dataset screen that lists, plays and deletes clips and exports one as a committed test fixture with the quiet lead-in and tail the tests need.
- The listener's state on the main screen (*untrained*, *recording*, *candidate ready*, *installed*, *listener down*), a mid-90s bulletin-board look, and three colour themes, *light*, *dark* and *sun*, switched with `T` and kept in the new `[tui] theme` setting.
- The `sherpa_kws` wake-phrase kind (`src/autobot/listener/engines/sherpa_kws.py`): sherpa-onnx's open-vocabulary keyword spotter, which needs no training, as a third detector kind and a baseline for the trained model. `make fetch-models` fetches its model into `models/sherpa-kws/`, and `sherpa-onnx` and `sentencepiece` are runtime dependencies. `evaluate.score_kind` scores it, or any detector kind, on the held-out real recordings through the listener's frame path, and the Candidate screen shows the baseline's figures in a last column at its default threshold 0.5; the column takes no part in the verdict (`python -m autobot.wakeword.evaluate MODEL --baseline` prints the same).
- A muted microphone is caught before a take is made: when the input has been digital silence for two seconds, the Recording session and the Audio screen show a NO SIGNAL line where the RMS meter is and say so on the message line, and in the session Enter and R ask before they record. A take that is digital silence is still flagged, as before.
- F1 shows the keys of the screen it is opened on (the session's Enter, P, R, D, N, B; the monitor's R, W, M, S; the Dataset screen's P, D, E; the training pane's S and C), then the keys that work everywhere, and names the menu keys only on a screen that is a menu.
- `make fetch-models` names each of the listener's model files as fetched or already there, the piper voice and the `sherpa_kws` model among them.
- ADR 0006, recording that the full-screen terminal user interface is the application and that the wake-word model is trained on the owner's voice first, superseding the parts of ADR 0005 it names.

### Changed

- `wake-word-listener-SPEC.md` gained rules WW-5 to WW-9: `autobot` as the first test wake phrase, detection by containment, a wake phrase's kind as the detector that implements it, the spoken acknowledgement, and running on the NUC only.
- `SCHEMA.md`, `ARCH.md`, `CONVENTIONS.md`, `GLOSSARY.md`, `INFRASTRUCTURE.md`, `AGENTS.md` and `README.md` now describe the built listener and control layers: the configuration file and `WakeEvent` shapes, the `run/listener.sock` seam, the Python conventions in force, the NUC's hostname and audio hardware, and the checks agents run (`make test`, `make lint`, `make typecheck`).
- The context documents, `README.md` and `AGENTS.md` no longer describe the WSL layer on the Windows dev server as a test machine; support is limited to the NUC.
- The larger synthetic training run of 2026-11-25 and three retrains of the classifier on its cached features did not make the model good enough for a house. Ten times the synthetic speech barely moved the curve of recall against false accepts: on text-to-speech voices kept out of training the model still missed about a third of `autobot` utterances at one false accept an hour. Leaving out the hard negatives that sound the same as the phrase helped only at low false-accept rates. The misses sat in accented voices, the bare phrase and slow renderings. Hence real recordings of the owner's voice first (ADR 0006).
- A fresh install starts on `kind = "text_match"` with threshold 0.5 and no model path; `openwakeword` is configured by installing a candidate. The synthetic-only `models/wakeword/autobot.onnx` on the NUC is kept as a leftover.
- `make train-wakeword` writes a candidate, `models/wakeword/candidate.onnx` and `candidate.json`, and no longer installs its result or asks for a threshold to be set by hand. It leaves the near-homophone hard negatives out of the training by default; `--no-exclude-near-homophones` trains on them.
- The acknowledgement is spoken in piper's Joe Medium voice, `en_US-joe-medium`, which `make fetch-models` fetches.
- The Audio screen's "save the clip" writes into the voice dataset, not into `tests/fixtures/audio/`.
- `make deploy` and the bare `make` summary call the terminal user interface the application.
- `wake-word-listener-SPEC.md` gained rules WW-10 and WW-11 (the score event; the recent stretches and the ten-second buffer held in memory), and WW-7 and WW-8 now name the three kinds, the fresh-install kind and the Joe Medium voice.
- `BRIEF.md`, `CONVENTIONS.md`, `ARCH.md`, `SCHEMA.md`, `GLOSSARY.md`, `INFRASTRUCTURE.md`, `AGENTS.md`, `README.md` and `tests/fixtures/audio/README.md` now describe the studio: the terminal user interface as the application, `data/voice/` and its manifest line, the `score` event, the real-set fields of the evaluation file, and fixtures exported from the Dataset screen. `headless-wake-word-prototype-PLAN.md` marks its steps 6 and 7 as superseded by the studio plan.
- A screen of the interface opens on the config file as it is at that moment, so an edit made by hand while the interface is open is read, not overwritten from memory; a file that no longer parses is one line and the last good configuration stays.
- On the Candidate screen the scroll note has a row of its own and no longer covers the last figure, and a candidate whose evaluation file cannot be read is refused in one line before the question.
- The `Makefile` no longer carries the "not built yet" stub helper or the path of the prototype plan: every target is built.

### Removed

- The wall UI, web interface and PWA are no longer planned (ADR 0006), and the context documents no longer describe them as parts to come.
- The terminal user interface's placeholder entries for cloud deployment and identity and access management.

### Security

- The listener disables `onnxruntime`'s usage telemetry (`ORT_DISABLE_TELEMETRY=1`, set before the library is imported, and in the systemd unit), which would otherwise make network calls from the speech path.
