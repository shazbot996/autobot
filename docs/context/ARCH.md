# autobot — Architecture

The architecture document is the map of autobot: the parts, how speech and data move between them, and the seams along which its specs divide. Three parts are built and are described here from the code: the listener, the wake-word training with its voice dataset, and the application's interface, a full-screen terminal user interface whose first job is the wake-word training studio. The `Makefile` beside them is the runtime control layer. The other parts are still the design the Smart Start intake describes, and each says so.

autobot is not one large process. It has two layers: a data plane that handles live audio, and a control plane above it that manages the rules. The owner reaches both by hand through one interface, the terminal user interface, and starts and stops the listener through the `Makefile` or that interface. The system supports the Ubuntu NUC alone.

The studio is built and its tests pass, and it has been run on the NUC with scratch data and a virtual audio source. It has not yet been used with the owner's voice: no session has been recorded, `data/voice/` does not exist yet, and no model has been trained on real recordings.

## What the parts are

- **Listener (data plane). Built.** The always-on local process that reads the microphone on the NUC and detects configurable wake phrases. It is the Python package `src/autobot/listener/`, run as `python -m autobot.listener`. It reads 16 kHz mono audio in 80 ms frames (`audio.py`), passes them through a speech gate built on Silero VAD so that silence never reaches a detector (`vad.py`), feeds the voiced frames to one detector per configured wake phrase (`detector.py`, `engines/`), publishes each wake as a `WakeEvent` and each stretch's detector scores as `ScoreEvent`s (`events.py`), and speaks an acknowledgement (`ack.py`). For the live monitor it also holds, in memory only, the audio of the last five stretches of speech, each with its pre-roll, and the last ten seconds of microphone audio (`RecentAudio` in `service.py`), and writes one of them to a file only when a control command asks. It is local for cost: always-on listening must cost nothing per second (`CN-1`).
- **Wake-word engines. Built.** A detector implements one wake phrase behind the `Detector` protocol: `feed` takes the next frame of a stretch of speech, `end_of_speech` says the stretch has ended, and `reset` makes the detector forget what it has buffered. Three kinds exist, one module each under `src/autobot/listener/engines/`. `text_match` is the kind a fresh install starts on, and the fallback: it transcribes each stretch of speech with faster-whisper (`tiny.en`) and fires when the transcript contains the phrase. It needs no trained model. `openwakeword` is the engine for 24x7 use: a small model trained here for the phrase `autobot` scores every frame it is fed, on openWakeWord's shared feature extractor, and the detector fires when the score reaches the phrase's `threshold`, then ignores the next two seconds so that one utterance is one wake (ADR 0005). Its three ONNX models are run with `onnxruntime` on the CPU, one thread each; the `openwakeword` Python package is not a dependency. It becomes the configured kind when the owner installs a trained model from the interface. `sherpa_kws` is the no-training baseline (TS-14): sherpa-onnx's open-vocabulary keyword spotter, a small streaming recogniser fetched into `models/sherpa-kws/`, with the configured phrase spelled in the model's own word pieces. It reports that it heard the phrase, not how sure it was. It runs in the listener as an engine, and `evaluate.score_kind` runs it, through the listener's own frame path, over the same held-out real recordings as the trained model: the Candidate screen shows its figures in a last column, at its default threshold only, since it gives no score to sweep.
- **Wake-word training and the voice dataset. Built.** `src/autobot/wakeword/`. The voice dataset (`dataset.py`) is the owner's recordings under `data/voice/` with one manifest, `manifest.jsonl`; it decides, and nothing else does, which clips are trained on and which are held out. The recording script (`script.py`) is the fixed list of prompts a session asks for. The training (`train.py`, run by `make train-wakeword`) synthesises the phrase, words that sound like it and ordinary speech with piper-tts in 20 voices, adds reverb and noise, and computes openWakeWord features; it cuts the training side of the voice dataset into the same windows; and it trains the classifier on both and on openWakeWord's general negative features, with half of every batch of positives and a third of every batch of negatives real when recordings exist. It evaluates on 7 synthetic voices it never trained on and, separately, on the held-out real recordings (`evaluate.py`), and writes a candidate, `models/wakeword/candidate.onnx` with `candidate.json`. It installs nothing. `install.py` moves a candidate into place, keeps the model it replaces as `<name>.prev.onnx`, writes `kind`, `model` and `threshold` to the configuration file, and can revert. With no recordings the training runs on synthetic speech alone and its evaluation says so.
- **Speech-to-text (STT).** Local transcription of the speech captured after a wake phrase, with faster-whisper (ADR 0003, accepted by ADR 0004). Not built as a part of its own: faster-whisper runs today inside the `text_match` detector, and in the training to find where the phrase ends in a recorded sentence. Never a cloud service (`CN-1`).
- **Rules layer (control plane). Not built.** Classic rules that validate a transcript, decide which kind of AI call it feeds, route it to an agent, or answer locally with low latency. This is the control plane above the listener, comparable to Dialogflow in Google Cloud: it is where the rules are managed. Rules accumulate over time into conversational pathways toward the planned agent tools. This is the "rules-first" part of rules-first AI agents.
- **Agent host. Not built.** The server-side part that defines persistent agents with Gemini ADK, opens interactive sessions with them against Gemini models in the owner's Google Cloud project, and persists each agent's state and memory locally. Creating new agents that serve from configured wake phrases and saving their state locally is a core purpose of this part (ADR 0002).
- **Text-to-speech (TTS).** Local synthesis in a configurable voice, with piper-tts (ADR 0003, accepted by ADR 0004). Its one use at run time is the listener's acknowledgement: the text in `[ack].text` is rendered once, when the listener starts, in the voice `[ack].voice` names, piper's Joe Medium (`en_US-joe-medium`), and that clip is played on every wake. Speaking an agent's response is not built. Never a cloud service (`CN-2`).
- **Terminal user interface (the application). Built.** A full-screen `curses` interface, `src/autobot/tui/`, opened by `make deploy`: autobot's application, not a control panel beside one (TS-1, ADR 0006). It is a front. It holds no configuration of its own, writes every setting to `config/autobot.toml`, and reaches the listener only through its control commands and its event stream. Its main screen always shows where the listener stands, as one of *untrained*, *recording*, *candidate ready*, *installed* or *listener down* (`state.py`), with what the voice dataset holds. The studio screens come first in its menu: **Recording session** (one prompt at a time, resumable), **Train the model** (the log of `make train-wakeword` as it runs), **Candidate** (the candidate's figures on the held-out recordings beside the installed model's, install, revert), **Live monitor** (the listener's scores and wakes as they happen, and marks that save an utterance into the dataset) and **Dataset** (every clip: play, delete, export one as a test fixture). The settings screens follow: Audio (devices, PipeWire's default microphone and speaker, a level meter, recording a test clip into the dataset), Wake phrase (threshold, kind, model path, playing the acknowledgement), Service (the systemd unit) and Host (naming this machine as the NUC). It is drawn like a mid-90s bulletin board in one of three themes, *light*, *dark* and *sun*; `T` switches. The recording session, the live monitor and the install refuse to run on any machine but the NUC.
- **Local store.** Where wake phrase configuration, rules, agent definitions and agent memory live on the local machine. The built parts are `config/autobot.toml`, the one configuration file; `models/`, the model files; and `data/voice/`, the voice dataset. Neither `models/` nor `data/` is committed, and the recordings never leave the NUC. The form of the rest is not yet decided; see `SCHEMA.md`.
- **Gemini agents (external). Not built.** The Gemini models in the owner's Google Cloud project that the ADK calls for agent reasoning. The only part that is not local.
- **Make (runtime control layer). Built.** A bare `make` prints a summary of every target. `make up`, `make down`, `make status` and `make logs` run `python -m autobot.listener.control`; `make deploy` opens the application; `make audio-check` checks the NUC's audio hardware; `make test`, `make lint` and `make typecheck` are the checks; `make setup` creates the environment; `make fetch-models` downloads the published model files into `models/`, and is the only target that downloads; `make train-wakeword` trains a wake-word candidate. `make deploy` is the only front-end target.

No wall UI, web interface or PWA is a part. The intake described a voice-driven screen on the wall; ADR 0006 withdrew it, and what the application shows, it shows in the terminal user interface.

## How they fit

What the listener does, on the NUC:

1. The listener runs continuously, as the systemd user unit `autobot-listener.service`. It reads the microphone through PipeWire and holds every model it needs as a local file.
2. Each 80 ms frame goes through the speech gate. Silence is dropped. A stretch of speech is released to the detectors with a few frames of lead-in so that the first syllable is not clipped. One VAD scores each frame once; a detector that needs wider margins is fed through a gate of its own, driven by the same score. The `openwakeword` detector asks for 0.96 s before the speech and 0.8 s after it, because its model wants to have heard what came before the phrase and scores highest just after the phrase ends; `text_match` and `sherpa_kws` take the default 0.24 s and 0.48 s.
3. The detector for each configured wake phrase is fed the stretch. When one hears its phrase, anywhere in the utterance, it returns a `WakeEvent`.
4. Each stretch gets an identifier, a counter that starts at 1 with each run of the listener. When the stretch ends, or just before the first wake inside it, the listener publishes one `ScoreEvent` per configured phrase to the readers of `run/listener.sock`: what that detector made of the stretch.
5. The listener writes each wake as one JSON line to its log and to every reader connected to `run/listener.sock`, after the score events of its stretch.
6. When the event's target is `ack`, the listener plays the acknowledgement ("Yes?") on the speaker. While it plays, and for a moment after, the microphone's audio is discarded and the detectors are reset, so the listener does not wake itself.
7. Meanwhile the listener keeps the last five scored stretches, each with its pre-roll and at most its last 30 seconds, and the last ten seconds of microphone frames, in memory. It writes neither anywhere on its own.

Nothing in those steps leaves the machine. The listener opens no network connection: every model is a local file under `models/`, a missing one is an error rather than a download (`make fetch-models` is the separate command that downloads them, and the listener never runs it), and the process sets its offline environment (`autobot.listener.models.enforce_offline`) before any speech library is imported. That step matters for `CN-1`: `onnxruntime`, which runs the VAD, the wake-word model and piper, otherwise uploads usage telemetry a few seconds after it is imported, and `ORT_DISABLE_TELEMETRY=1` is what switches that off.

The studio is the loop that makes the listener hear the owner. It is driven from the terminal user interface:

1. On a fresh install the phrase's kind is `text_match` and the main screen reads *untrained*. A model file at the phrase's model path that the configuration does not name as `openwakeword` is a leftover: kept, not counted as installed, and not compared.
2. A recording session asks for the speaker's name and shows the script one prompt at a time: the phrase bare, with "hey" and "yo", inside a sentence, slow, fast, quiet, raised, near and far; words that sound like it and ordinary sentences; and five one-minute prompts of the room with nobody speaking. An optional sixty-minute room recording follows. Each take is written to `data/voice/` with a manifest line the moment it is accepted, so a session resumes at the first prompt not yet answered.
3. `make train-wakeword`, started from the interface or from a shell, trains on the dataset and the synthetic speech and writes a candidate. It touches neither the installed model nor `config/autobot.toml`.
4. The Candidate screen scores the candidate and the installed model on the current held-out recordings and compares them. With a held-out set of at least twenty positives, twenty negatives and twelve minutes of ambient audio it gives a verdict, and offers the install only when the candidate is at least as good; below that size it shows the figures and offers an install on the owner's own judgment. With nothing installed there is nothing to beat. The threshold an install writes is the one recommended in that scoring, on the held-out set as it is now; the evaluation file's is used only when nothing is held out. A last column shows the `sherpa_kws` baseline on the same recordings; it is there to be read and takes no part in the verdict.
5. An install the owner confirms moves the candidate to the phrase's model path, keeps what was there as `<name>.prev.onnx`, and writes `kind = "openwakeword"`, the `model` path and the recommended `threshold` to the configuration file. A revert swaps the two back. The interface then offers to restart a running listener, which loads its model when it starts.
6. The Live monitor reads `run/listener.sock`. The owner marks a detection right or wrong, or marks that a wake was missed; the interface runs `control snapshot` for that stretch, or for the last ten seconds, and adds the audio to the dataset with `source = "monitor"`. Those clips join the next training run.

The recordings never leave the NUC in any of those steps (TS-5). The one copy that leaves `data/voice/` is a fixture the owner exports, clip by clip, into `tests/fixtures/audio/`.

The full exchange the intake describes continues from the wake event, and is not built:

1. The wake phrase's target selects an agent or rule set, and the listener captures the speech that follows.
2. STT transcribes the capture locally.
3. The rules layer validates the transcript. If a rule can answer locally, it does so at once, with low latency. Otherwise a rule decides which kind of AI call the query feeds and routes it to an agent.
4. The agent host opens or continues a session with that agent through Gemini ADK. The reasoning runs against Gemini in Google Cloud; the agent reads and writes its memory in the local store.
5. The response comes back as text. TTS speaks it in the configured voice.

Only the agent reasoning leaves the machine, and only as text. Audio never does.

Runtime control stands beside this flow, not in it. `python -m autobot.listener.control` has two modes behind one set of commands. Without the systemd unit installed, `make up` starts the listener in the background with its pid in `run/listener.pid`. With the unit installed, which it is on the NUC, the same commands drive `systemctl --user`. Either way the listener's output goes to `run/listener.log`. The unit is rendered from the template `deploy/autobot-listener.service` into `~/.config/systemd/user/`; it restarts the listener after a fault that may pass (exit status 1, such as the audio device not being ready) and leaves it down after one that will not (exit status 2, such as a bad configuration or a missing model). With the unit enabled and lingering on for the user, the listener starts at boot with nobody logged in. The terminal user interface drives the listener only by running those commands as subprocesses and by reading its socket; it does not import the listener.

## The seams

1. **Wake-word listener**: the microphone stream, wake phrase detection, and the hand-off to what comes next. This is the seam between the data plane and the control plane, and its built form is `run/listener.sock`: a Unix domain stream socket, mode 0600, that the listener binds while it runs. Any number of readers may connect; each event is broadcast as one JSON line to the readers connected at that moment, with no backlog and no replay, and a reader that falls behind is dropped rather than allowed to block the audio loop. Two events travel on it: `wake`, which also goes to the log, and `score`, which goes to the socket only, so the log holds what it always held. The log holds the history of the wakes. The capture of the speech after the wake, and its hand-off to STT, are not built. Governed by [wake-word-listener-SPEC.md](../specs/active/wake-word-listener-SPEC.md).
2. **Detector kinds**: inside the listener, the `Detector` protocol in `src/autobot/listener/detector.py`. A new kind of wake phrase is one new module under `engines/`, found by its name, plus its name in the list of valid kinds in `src/autobot/config.py`.
3. **Rules-first routing**: the transcript in, and either a local response or a validated, routed query out. Governed by [rules-first-routing-SPEC.md](../specs/active/rules-first-routing-SPEC.md).
4. **Agent sessions**: agent definitions, sessions through Gemini ADK, and locally persisted memory. Governed by [agent-sessions-SPEC.md](../specs/active/agent-sessions-SPEC.md).
5. **Spoken response**: the text response in, spoken audio in a configurable voice out. No spec yet.
6. **Voice dataset**: `data/voice/manifest.jsonl` and the WAV files beside it. The interface writes it (the recording session, the live monitor's marks, the Audio screen), and the training and the evaluation read it. The split between trained and held-out audio is computed from the manifest line alone, in `src/autobot/wakeword/dataset.py`, so every reader agrees on it. Governed by [autobot-wake-word-training-studio-SPEC.md](../specs/active/autobot-wake-word-training-studio-SPEC.md).
7. **Candidate and install**: a training run's output, `models/wakeword/candidate.onnx` with `candidate.json`, in; the installed model at the phrase's model path and three lines of `config/autobot.toml` out, through `src/autobot/wakeword/install.py` and only on the owner's confirmation. Governed by the same spec (TS-8).
8. **Runtime control**: the subcommands of `python -m autobot.listener.control` (`up`, `down`, `status`, `logs`, `snapshot`, `install`, `uninstall`, `enable`, `disable`). The `Makefile` and the terminal user interface both go through them, so there is one implementation of starting and stopping the listener. `snapshot --stretch ID` and `snapshot --buffer` are how the live monitor gets audio out of the listener: the command writes `run/snapshot.request`, signals the listener with `SIGUSR1`, and waits up to five seconds for `run/snapshot.wav`, or for the listener's one-line reason in `run/snapshot.error`. The socket stays one-way.

The wall UI seam of earlier versions of this document is withdrawn with the part (ADR 0006).

## Open Questions

- Do the agent host and the local store sit in the control plane with the rules layer, or in a third process of their own?
  The listener is a separate data-plane process from the rules layer, but the split between the rules layer and the agent host is not stated.
- How is the control plane's rule definition turned into what the listener runs, and is that a compile step?
  The listener is "probably compiled somehow" from the control plane. Today the listener reads `config/autobot.toml` when it starts, and nothing is compiled.
- Does the rules layer read `run/listener.sock` as a separate process, as the seam allows, or is it loaded into the listener's process?
- Where does the capture of the speech after a wake happen: in the listener, which already holds the microphone, or in whatever reads the `WakeEvent`?
- Where do the rules layer and the agents appear in the terminal user interface? TS-1 says later jobs of the application are further screens of the same interface, and none is designed yet.
