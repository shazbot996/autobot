# autobot — Google Cloud configuration screen

The **Google Cloud** screen is a full-screen editor in the configuration menu, the same kind of screen as the Agent editor. It walks the owner through connecting autobot to the Google Cloud project `schiele-autobot-dev` in this order: set the project, check the APIs, create a dedicated service account with its IAM bindings, create that account's key, set up Secret Manager and the secrets autobot expects, choose the Gemini API and model, set rate limits, and show the Cloud Storage buckets. At each step the screen checks what is already in place. When something is missing it shows the commands that fix it, and the owner copies them and runs them himself. autobot never configures itself in Google Cloud: the owner's account is privileged (owner, with billing rights), so autobot and its agents run only as the service account, and the one value the screen sends to the cloud itself is a secret the owner pastes in. Rules GC-1 to GC-13 govern the screen. It builds on the agent tree spec (AG-6, AG-8, AG-10, AG-12), the agent sessions stub (AS-1, AS-2), the studio spec (TS-10, TS-13), ADR 0002 and `CN-1` and `CN-2`. The screen was built from `docs/plans/active/google-cloud-configuration-screen-PLAN.md` and then corrected against the real project on 2026-11-27; this revision records the screen as it stands.

## Numbered rules, each with its reason

1. **GC-1. The Google Cloud screen is a full-screen screen of the configuration menu, walked one step at a time.** The main menu in configuration mode (AG-8) gains a **Google Cloud** entry, after **Agent routing**. It opens a full-screen screen that lists the steps in order, numbered 1 to 8: **Project**, **APIs**, **Service account**, **Key**, **Secret Manager**, **Gemini**, **Rate limits**, **Cloud Storage**. Each step shows one of four states: *ready*, *missing*, *unchecked* (it cannot be checked yet, and the label says why, as *unchecked: no service account key yet*) or *not used yet*. Until the first round of checks has finished, every step reads *checking...*. Up and Down move between steps, and the list shows the selected step's purpose and findings under it. Enter, or the step's digit, opens a step: what it is for, what was checked and found, the fields Enter changes when it has any, the commands that fix what is missing, and, last, the read-only commands the owner can check the step with himself ("To look for yourself: these change nothing"). In an open step Up and Down move between its fields, PgUp, PgDn, Home and End scroll it, and Escape, Left or Backspace returns to the list. Each step builds on an earlier one: APIs on Project, Service account on APIs, Key on Service account, and Secret Manager, Gemini, Rate limits and Cloud Storage on Key. A step whose earlier step is not *ready* says so: "Builds on Key, which is not ready yet." `R` checks every step again, and the checks run on a thread, so the frame never waits for them. F1 lists the screen's keys. Reason: the owner wants "another full-screen application editor screen that we invoke from the configuration menu", like the agent tree, and wants it to "walk me through each step", because setting up a service account and its key "is a tricky process". The order is the order the setup works in: the project comes first, the APIs must be on before the service account can be created, and the account must exist before its key can be made or its permissions checked.

2. **GC-2. The application shows commands. It never runs a command that changes Google Cloud.** Every change to the project is a `gcloud` command shown on the screen, filled in with the configured project, region and account and shell-quoted. This covers enabling an API, creating the service account, granting a role, creating the key, creating a secret, creating and restricting the weather API key, and setting a quota cap. An open step is drawn without the frame's side borders, and each command is drawn alone on its own rows from the left edge, with nothing beside it, so that selecting it with the mouse copies the command and nothing else. Above each command its purpose stands as a shell comment (`# Create the account's key, straight into its file`), and the heading of a block of commands is a comment too, so a selection that takes them in still pastes. A command longer than the screen is continued onto the next row with a trailing backslash, never broken inside single quotes, so the rows pasted together are still the one command. `W` writes the open step's commands as a shell script, `run/gcp/<step>.sh` (`project.sh`, `apis.sh`, `service-account.sh`, `key.sh`, `secrets.sh`, `gemini.sh`, `quotas.sh`, `storage.sh`), for the owner to read and run with `bash`; the script starts with `set -euo pipefail` and moves to the repository root, so a relative key path lands where the configuration says. When a step has no fix commands `W` writes its read-only ones, and when it has neither it says so and writes nothing. The application never runs those commands or the script, by itself or through a subprocess. The only change it makes in Google Cloud is adding a secret value the owner pastes in (GC-9); the only changes it makes on this machine are the three settings it writes to `config/autobot.toml` (GC-3, GC-11) and the scripts under `run/gcp/`. Reason: the owner said "I don't want the agent to be able to configure itself, but I would like it to be able to offer me the script to do it". Commands the owner runs in his own shell run with his own credentials, which never enter autobot. `run/` is git-ignored runtime state.

3. **GC-3. The project and region are settings in `config/autobot.toml`.** The Project step sets `[gcp] project`, which is `schiele-autobot-dev`, in the Google Cloud organization `cambiumplatform.com`, whose domain and organization the owner owns, and `[gcp] region`, which is `us-east5`. They are two fields of the step, **Project** and **Region**; Enter on one opens a text field that refuses anything that is not a project id (6 to 30 lower-case letters, digits and hyphens) or a region (as `us-east5`), and the value is written to the file at once, creating the `[gcp]` table when the file has none. Every command and check uses them. The step reads *missing* when `[gcp] service_account` is not an account of the configured project, and says to edit the configuration file. The step also shows the commands the owner uses to point his own `gcloud` at the project and keep his own login and Application Default Credentials up to date (`gcloud config set project`, `gcloud auth login`, `gcloud auth application-default login`), as commands for his shell only, and `gcloud projects describe` as the read-only check. Reason: the owner said "the first thing this application should do is allow you to set the GCP project". Configuration lives in one file, and the interface holds none of its own (TS-10, `CONVENTIONS.md` "Layout").

4. **GC-4. autobot and its agents use Google Cloud only as the dedicated service account, never as the owner.** autobot finds its credentials through Application Default Credentials, which the application always points at the service account's key file (GC-7) for itself and the agents it runs, by setting `GOOGLE_APPLICATION_CREDENTIALS` to the key's path before it asks for default credentials. It never asks for default credentials without a *ready* key, so it cannot fall back to the owner's own default credentials. Before any cloud call, the application checks which identity the credentials resolve to. If they are not service-account credentials for the configured service account (`[gcp] service_account`), the connection is refused before a single call is made, the environment variable is put back as it was, and the reason is one line: `refused: credentials resolve to <identity>, not <service_account>`. A refusal makes the Key step *missing*, with the refusal under the line that says the file itself is safe, and every account-dependent step *unchecked* with the same line. Until the key exists, every check that needs the account reads *unchecked: no service account key yet*, and the step shows everything the step sets up and the read-only `gcloud` commands the owner can run to check it himself, all for his own shell. When Google Cloud answers a check with 403, the step says that the service account was refused, most likely because its roles are not granted yet, and to run the grants on the Service account step, wait a minute and press `R`. The application does not run any check with the owner's own login. Reason: the owner wants "to just use application default credentials", but wants "this application to [run] its commands through a service account that we create because this account is privileged, it's the owner, and it has billing rights to everything, and so I don't want the agent running with those credentials". Default credentials pointed at the account's key give both. Refusing any other identity stops a missing key from quietly falling through to the owner's login. Before the key exists, the screen guides the owner through setting the application up and only shows him commands, so his credentials never pass through the application. Role grants take a minute to apply, and saying so saves the owner a search.

5. **GC-5. The APIs step checks every API autobot needs and shows the command to enable the ones that are missing.** The step lists the APIs that autobot's steps and agents use, shows whether each one is enabled in the project, and for the missing ones shows one `gcloud services enable` command naming them all, for the owner to run with his own credentials. The first set is below. An agent that starts calling a new Google API adds it to the list.

   | API | Needed for |
   |---|---|
   | `serviceusage.googleapis.com` | checking which APIs are enabled, and reading quotas |
   | `cloudresourcemanager.googleapis.com` | the permission check (GC-8) |
   | `iam.googleapis.com` | creating the service account and its key |
   | `secretmanager.googleapis.com` | the secrets (GC-9) |
   | `aiplatform.googleapis.com` | Gemini on Vertex AI, when that is the chosen API (GC-11) |
   | `weather.googleapis.com` | the `weather` agent's lookup (AG-6) |
   | `apikeys.googleapis.com` | creating and restricting the weather API key |
   | `cloudquotas.googleapis.com` | setting the caps (GC-10) |

   The list follows the configuration: `aiplatform.googleapis.com` is on it only when Vertex AI is the chosen Gemini API, `generativelanguage.googleapis.com` joins it when the Gemini Developer API is chosen, and `storage.googleapis.com` joins it when `[gcp] buckets` lists a bucket (GC-12). The same list is the allowlist of hosts the application may connect to (GC-13). Reason: the owner asked for "an API check, and if we're missing APIs, again, we should show [commands] that we can cut and paste with privileges to enable those APIs". The owner enables the APIs, because the service account is not allowed to (GC-6).

6. **GC-6. The service account gets the narrowest roles that cover what autobot does, and never a broad one.** The Service account step shows the commands that create the account `[gcp] service_account` (by default `autobot-agent@schiele-autobot-dev.iam.gserviceaccount.com`) and grant its roles, one at a time, each with a line saying what the role lets autobot do. The create command first asks whether the account exists and creates it only when it does not, so the line can be run again; each project grant carries `--condition=None`, so `gcloud` does not stop to ask. Where a role can be granted on a single resource, such as one secret or one bucket, it is granted there rather than on the project. The first set:

   | Role | Granted on | Lets autobot |
   |---|---|---|
   | `roles/serviceusage.serviceUsageViewer` | project | see enabled APIs and quotas |
   | `roles/serviceusage.apiKeysViewer` | project | check how the weather key is restricted |
   | `roles/aiplatform.user` | project | call Gemini on Vertex AI (GC-11); left out when Vertex AI is not the chosen API |
   | `roles/cloudquotas.viewer` | project | read the live limit of each capped quota (GC-10) |
   | `roles/secretmanager.viewer` | each expected secret | see that the secret exists and has a version |
   | `roles/secretmanager.secretAccessor` | each expected secret | read the secret's value at run time |
   | `roles/secretmanager.secretVersionAdder` | each expected secret | store a pasted value (GC-9) |
   | `roles/storage.objectViewer` | each configured bucket | list and read the objects in the bucket (GC-12) |
   | `roles/storage.objectCreator` | each configured bucket | write new objects to the bucket (GC-12) |

   `roles/cloudquotas.viewer` is there because reading a quota's live limit by its id goes through the Cloud Quotas API, whose read permission none of the other roles holds; it is read-only. The step's state is the permission check of GC-8 on the project. It also asks whether the account holds any permission only a broad role grants (`resourcemanager.projects.setIamPolicy`, `serviceusage.services.enable`, `iam.serviceAccounts.create`, `iam.serviceAccountKeys.create`, `resourcemanager.projects.createBillingAssignment`, `billing.resourceAssociations.create`) and flags each one held as *too broad*, naming the roles that commonly grant it (`roles/owner`, `roles/editor`, the IAM, service-usage and billing admin roles). The fix it shows is the `remove-iam-policy-binding --all` command for each of those roles, with the read-only `gcloud projects get-iam-policy` command, filtered to the account, that lists the roles it actually holds, and a note to remove the broad one that command shows. Reason: the whole point of the account is that the agent does not run with the owner's privileges. Giving it a role that lets it enable APIs, grant itself roles or spend money would defeat that, and would let the agent configure itself, which the owner does not want (GC-2). Asking about marker permissions rather than reading the IAM policy needs no extra grant, because none of the roles above may read the policy.

7. **GC-7. The key is created by a script the owner runs, kept git-ignored, and only its path is in the configuration.** The Key step shows a script, also offered through `W` (GC-2). The script sets `umask 077`, makes the key's directory and sets it to `0700`, creates the service account when it does not exist yet (the same line as the Service account step, because a key cannot be made for an account that is not there and the owner may start at this step; the account's roles are still granted on the Service account step), creates the account's JSON key straight into the path in `[gcp] credentials_file` (by default `secrets/service-account-autobot-agent.json`; `.gitignore` covers `secrets/` and the `service-account*.json` pattern), and ends in `chmod 600` on the key. It never prints the key. The step reports *ready* only when the file exists and is a regular file, `git check-ignore` confirms that git ignores the path, the file has no group or other permission bits, and it belongs to the current user. If git does not ignore the path, or cannot say, the step reports *missing* with the reason (`git does not ignore secrets/…: the key is not used`), and the application does not use the key. A key that is safe but resolves to another identity is reported as GC-4 says. The read-only command is `gcloud iam service-accounts keys list`. The application reads the file's metadata only: it never shows the key's contents, never copies the key, and never writes it anywhere else. Reason: the owner called "conveying of the key" "the dangerous part" and asked for "scripting the download of the JSON, keep it in the git-ignore". A key that git does not ignore is one `git add` away from being committed, and `AGENTS.md` keeps credentials out of the repository. A key file is used rather than default credentials that impersonate the service account, because impersonation keeps the owner's refresh token where the application could reach it. The key is the only way the agent never holds the owner's credentials.

8. **GC-8. The permission check proves that the account can do everything autobot needs.** Once the key is *ready*, the screen asks Google Cloud which of the permissions autobot needs the account actually holds (`testIamPermissions` on the project, on each expected secret and on each configured bucket). It lists each needed permission as held or missing, and for a missing permission it names the GC-6 role that grants it and shows the grant command. A permission that cannot be tested on a kind of resource is asked for alone and counted as not held, so one such permission does not fail the whole check. The Service account step takes its state from the project's permissions, the Secret Manager step from each secret's, the Cloud Storage step from each bucket's, and the Gemini step from `aiplatform.endpoints.predict` on the project. Reason: the owner wants the screen to "test that it has the privileges" so "that it is comprehensive in the APIs and permissions that it has". Asking for the permissions themselves finds a missing grant before an agent fails on it in the middle of a session.

9. **GC-9. Secret Manager holds every secret autobot expects, and a pasted secret goes nowhere but Secret Manager.** The Secret Manager step first checks that the API is on and the account can reach it. If not, it shows the commands from GC-5 and GC-6. It then lists every secret that autobot's configuration expects, each one named by the agent definition that needs it. The first is the `weather` agent's API key, `autobot-weather-api-key` (AG-6). For each secret it shows whether the secret exists (the account can see it), what the account may do on it, and how many enabled versions it has, and never shows the value. A secret that does not exist, or that the account holds nothing on, gets the `gcloud secrets create` command, with user-managed replication in `[gcp] region`, and its three per-secret role grants, for the owner to run; a secret with a missing grant gets that grant. Each secret is a field of the step. Enter on a secret that exists and that the account may add a version to opens a masked field: each typed or pasted character is drawn as `*`, the field says how many characters it holds and that they are not shown, Backspace and Ctrl-U edit it, and Escape clears it and changes nothing. The owner pastes the value, the application adds it to Secret Manager as a new version through the service account, and then clears it from memory, whether the call worked or not. A pasted value is never written to `config/autobot.toml`, `run/`, a log, the screen or any other file, and a failed store is one line naming the secret and the cause, never the value. Enter on a secret that is not ready for a value says to run its create and grant commands, then press `R`. The Agent editor's edit of the weather API key (AG-10) uses this same path. For the weather key, the step also looks the API key up by its display name, `autobot-weather`, through the API Keys API, never by its value: with no such key it shows the command that creates one restricted to `weather.googleapis.com`; with a key that can call any other API it shows the command that restricts it; and when the secret is empty and the key exists it shows a command that pipes the key's value from one `gcloud` straight into `gcloud secrets versions add --data-file=-`, so the value is never shown and never passes through autobot, and beside it the command that prints the value for the owner to paste into the masked field instead. Reason: the owner wants the screen to "configure a secret manager once it's working, so again if it's not working, show me the code to enable it", to manage "the secrets that we expect to store in secret manager … from here", and to "paste in the credentials without ever persisting them anywhere except for secret manager". Restricting the key to one API limits what a leaked key could be used for.

10. **GC-10. Every billed API that an agent calls has a cap in Google Cloud, and the screen shows that the cap is in place.** The configuration records the intended cap for each billed API as `[[gcp.quotas]]` entries: the API, the quota id as `metric` (the id `gcloud beta quotas info list --service=<api>` prints; the cap's period, a day or a minute, is part of the id), the `limit` the live quota may not exceed, and, for a quota that is counted per model, an optional `base_model`. The Rate limits step reads the live limit of each entry through the Cloud Quotas API. A quota whose id names a region is compared in `[gcp] region`; a quota whose id names a base model is compared for the entry's `base_model`, or for `[gcp] gemini_model` when the entry names none, and with no model anywhere the entry reads *missing* with a line saying to choose the model on the Gemini step or add `base_model`. An entry reads *ready* when the live limit is at or below the intended one. It reads *missing* when there is no cap or the cap is higher, with the `gcloud beta quotas preferences create` command that sets the cap, with `--allow-high-percentage-quota-decrease` and the region and model dimensions it needs, for the owner to run; and *missing* when the API has no quota with that id, with the command that lists the ids so the entry can be corrected. A billed API that an agent calls but that has no entry (the weather API and the chosen Gemini API are the billed ones) is listed as a warning, *no cap*, with the line that nothing in Google Cloud limits it and the command that lists its quotas; it does not make the step *missing*, because leaving an API uncapped for now is the owner's to decide and the step says plainly that it is so. The read-only commands are `gcloud beta quotas info describe` for each entry. The entries today: the Weather API has no quota for the API as a whole, so each of its seven endpoints (current conditions, daily, hourly and minutely forecasts, history, map tiles, public alerts), whether or not an agent calls it, is capped at 100 requests a day and 10 a minute, fourteen entries, so that a leaked key is capped whatever it asks for. Gemini on Vertex AI has no entry for now, by the owner's decision of 2026-11-27: its request quota is counted per model and per region, and Google's own limit for the chosen model in `us-east5` is already below the 10 a minute that was intended, so asking for 10 was refused as an increase; the step notes that the API is billed and uncapped, and the configuration file carries the entry to add when a cap is wanted. The owner expects about 50 weather lookups a day, so 100 a day is twice his expected use, and the per-minute caps stop a runaway agent within minutes, at the cap and not at the bill. The cap in Google Cloud is the backstop behind the agent's own rate control (AG-6), not a replacement for it. Reason: the owner wants "real constraints on the rate limit" as "a safeguard" around any API "this application's agents ever might use", Maps above all because it is "very commonly abused" and his use is "just home use". He cannot translate his usage into a limit, so the screen's job is to show plainly that a limit exists and what it is.

11. **GC-11. The Gemini step shows which Gemini API and model autobot uses and checks that the account can call it.** `[gcp] gemini_api` names the API the `question` agent's ADK agent calls (AS-1, AG-5). It is set to Vertex AI (`aiplatform.googleapis.com`, authenticated as the service account, in `[gcp] region`, `us-east5`). The other choice is the Gemini Developer API (`generativelanguage.googleapis.com`, authenticated with an API key kept as a secret under GC-9); its key is not yet a secret autobot expects, and the step says so. `[gcp] gemini_model` names the model the agent calls; the first is `gemini-3.5-flash-lite`. The step shows the choice of API, checks that the API is enabled (GC-5) and that the account holds `aiplatform.endpoints.predict` (GC-8), and shows the commands that fix whatever is missing. It has one field, **Model**: Enter lists the Gemini models Vertex AI offers at that moment, asked as the service account, newest first, opening on the one chosen now, with a last entry for typing another model's id; the choice is written to `[gcp] gemini_model` at once and every step is checked again, since a per-model cap (GC-10) follows the model. The step reads *missing* when no model is chosen, or when the chosen one is not a model the API offers now. When the models could not be listed (the Developer API lists them only to an API key), the step says so, the model is not checked against the API, and it can still be typed. Discovery Engine (`discoveryengine.googleapis.com`) serves search and grounding, not Gemini models, and is not on the list unless an agent comes to need it. Reason: the owner said "we have to pick the Gemini API we're going to use and also show that here and check the permissions", and asked for help telling the APIs apart. He chose Vertex AI in `us-east5`. Vertex AI fits GC-4, because the service account needs no extra API key. Listing the models from the API, rather than from a list in the code, keeps the choice current as models are released and retired.

12. **GC-12. The Cloud Storage step shows the configured buckets and checks the account's access to them. Nothing stores state there yet.** `[gcp] buckets` lists the buckets autobot is meant to use. It is empty today, and the step reads *not used yet*, with the line that agent state and memory stay on the NUC. For each bucket listed, the step checks that the Cloud Storage API is enabled, that the bucket exists, and that the account holds the permissions autobot needs on it (`storage.objects.get`, `storage.objects.list`, `storage.objects.create`, GC-8). For anything missing, it shows the commands: `gcloud storage buckets create` in `[gcp] region` with uniform bucket-level access, and the two GC-6 roles granted on the bucket itself. This spec does not move agent state or memory into a bucket. They stay on the NUC (AS-2, ADR 0002) until a later decision says otherwise. Reason: the owner expects "a cloud storage bucket or two" for state and says "that's a future. We're not doing that yet. But this application will need to at least show it. And test that it has the privileges". There is no defined use for Cloud Storage today. The step stays in scope so the screen is ready for future agents that may use it. ADR 0002 and `AGENTS.md` keep agent memory and state on the local machine, and only a new decision can change that.

13. **GC-13. Only configuration and text reach Google Cloud. Failures are one line, and the logic is testable without a terminal or a network.**
    - **Speech.** Nothing on this screen sends audio, transcripts for recognition, or text for synthesis to any cloud service (`CN-1`, `CN-2`).
    - **Network.** In configuration mode, the screen connects only to the REST endpoints of the Google Cloud APIs on the GC-5 list, as the service account, to run its checks, list the Gemini models and add a pasted secret, and to Google's sign-in host, where the key is exchanged for a token. A call to any other host, or over anything but HTTPS, is refused before it is made. It calls the APIs directly: no Google Cloud client library beyond the one that signs the calls, and no speech library.
    - **Failures.** A failed check, a refused identity (GC-4), a missing key or an unreachable API is one line naming the cause, never a traceback (`CONVENTIONS.md` "Language and formatting"). A failed call turns only the step that made it into *unchecked* with that line; the other steps stand. A failure the screen itself hits is one line in the message bar.
    - **Testable.** The step model, the checks, the generated commands and scripts, the key-file check, the identity check, the folding of a command and the store of a secret live in modules that do no drawing. They are tested against the fake Google Cloud in `tests/gcp/gcp_fakes.py`, and the screen against the scripted fake terminal, and never with a real key or a network connection (`CONVENTIONS.md` "Testing", "Control layers"). The key file a test needs is an empty stand-in in a temporary directory.

    Reason: the constraints forbid any cloud speech path. The interface keeps its logic out of the drawing code so that it can be tested. A test that reached Google Cloud would need a credential, which `AGENTS.md` forbids an agent to read.

## Settled without asking

- **Derived (config/autobot.toml, src/autobot/gcp/needs.py).** The fourteen Weather API caps, the absence of a Gemini cap and the extra roles for quotas and buckets are what the project and the code hold today; GC-6 and GC-10 now say so.
- **Resolved.** GC-2 said the only change the screen makes is a pasted secret, while GC-3 and GC-11 have it write `project`, `region` and `gemini_model` to the configuration file. GC-2 now says the secret is its only change in Google Cloud, and names the file writes and the scripts as its only changes on this machine.
- **Resolved.** GC-10 listed a billed API without an entry as *missing*; the step shows it as a warning so that the owner's decision to leave Gemini uncapped does not keep the step from reading *ready*. GC-10 now says so.
