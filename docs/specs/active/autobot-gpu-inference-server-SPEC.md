# autobot — GPU inference server

The **inference server** is a second program of autobot that runs on `GAMEON1`, the owner's Windows PC with an RTX 2080 Ti, inside its Ubuntu WSL2 distribution, and serves the NUC over the LAN. It does three jobs the NUC's CPU does slowly or not at all: **speech-to-text** with a larger Whisper model than `tiny.en`, **routing**, a local language model the rules layer may consult when no rule matches, and **chat**, a local language model behind the core conversational agent; **text-to-speech** may follow. The NUC stays the front end: the wake word, the microphone, the speaker, the face, the rules layer, the agents and all agent state stay there, and every one of them keeps working when the server is away. The server is a stateless function of its requests: it keeps no session, no memory and no audio. Rules IS-1 to IS-14 govern it; the host itself is described in `docs/context/INFRASTRUCTURE.md`. The spec is a **draft**: several of its rules cannot take effect until the owner settles the open decisions marked **[open]** below and in Open Questions, three of which touch `CONSTRAINTS.md`, ADR 0002 and `CONVENTIONS.md`. It builds on `CN-1`, `CN-2`, TS-5, TS-11, RR-1, RR-3, AS-1, AS-2, AG-4 and GC-4, and amends nothing until those decisions are made.

## Numbered rules, each with its reason

1. **IS-1. The server runs on `GAMEON1`, in WSL, and nowhere else; the NUC is the only client.** It runs inside the `Ubuntu-24.04` distribution on `GAMEON1` and uses the GPU through the WSL driver. It serves the NUC and no other machine, and the NUC's front-end paths (the listener, the studio, the face, `make audio-check`) never run on this host: TS-11's hostname checks stay as they are. Reason: the owner added this host to be the GPU inference server on the LAN while the NUC "stays the front end (wake word, mic, speaker, face display)". One client keeps the server's surface and its firewall rule (IS-13) as small as they can be.

2. **IS-2. The server speaks HTTP with JSON on one TCP port, proposed `8300`, bound to the LAN address.** Every endpoint is under one port, given in `config/autobot.toml` (IS-3) and, for the firewall, in `INFRASTRUCTURE.md`. The port is proposed as `8300` because the `assistant` project already uses 8099, 8123 and 8199. **[open]** Whether streaming speech-to-text later needs a WebSocket on the same port. Reason: one port is one firewall rule and one thing to test from the NUC; HTTP and JSON need nothing on the NUC beyond the standard library or a small client, and are what local LLM runtimes already speak.

3. **IS-3. The NUC finds the server through `config/autobot.toml`, by address.** A new table (proposed `[server]`) holds at least the server's base URL (proposed `http://192.168.86.53:8300`), whether it is enabled, the request timeouts and the health-check interval. The NUC names the server by its reserved address, not by `gameon1.lan`. The table's exact fields are for `SCHEMA.md` when the client is built. Reason: `CONVENTIONS.md` keeps all configuration in that one file, and an address held by a DHCP reservation does not depend on the router's DNS staying up.

4. **IS-4. The NUC never depends on the server.** Every call to the server has a short timeout. The NUC keeps a health check of the server and shows its state on the main screen beside the listener's. While the server is down, asleep, off, or answering slowly, the NUC falls back without being told to: speech-to-text to its local faster-whisper `tiny.en`, text-to-speech to its local piper, routing to the rules alone (RR-1), and chat to the Gemini agents of AS-1 or to a spoken "the server is away". A wake is never lost and the listener never waits on the network. Reason: the NUC is on 24x7 and the PC is not; Windows Update restarts and the owner's own use of the PC will take it away, and an assistant that goes deaf with it would be worse than one that is slower.

5. **IS-5. The server is stateless and keeps no agent state or memory.** Each request carries everything the server needs: for chat, the agent's prompt and the conversation so far, which the NUC sends from its own store. The server keeps nothing between requests beyond the models loaded in memory, and writes no request or response to disk, except a log line of method, endpoint, size, duration and status. Reason: ADR 0002 and AS-2 keep agent state and memory on the local server, the NUC, and `AGENTS.md` forbids moving them off it. A stateless server also restarts and falls away (IS-4) without anything to lose.

6. **IS-6. Audio sent to the server is transcribed and dropped.** The server holds an utterance's audio only in memory and only while it transcribes it. It never writes audio, features or transcripts to disk and never forwards them anywhere. The owner's voice dataset (`data/voice/`) is never sent to this host, and no wake-word training runs here. Reason: TS-5 keeps the recordings and anything computed from them on the NUC; live utterances are not the dataset, but the same reasoning about the sound of the house applies, and a server that keeps nothing cannot leak it.

7. **IS-7. The server reaches no cloud service and holds no Google Cloud credential.** It opens no outbound connection at run time: models are loaded from local files, the speech libraries are imported behind `enforce_offline()` as `CONVENTIONS.md` "Local-only speech" requires, and telemetry is off. Downloading models is a separate, deliberate command, as `make fetch-models` is on the NUC. No service account key, `gcloud` login or Secret Manager access exists on this host; Gemini, when an agent uses it, is still called by the NUC as the service account (GC-4). Reason: `CN-1` and `CN-2` forbid a cloud service in the speech path, and keeping the one credential on the NUC keeps GC-4's single identity in one place.

8. **IS-8. Speech-to-text: `POST /v1/stt`.** The request is one utterance as a WAV body, 16 kHz, mono, 16-bit PCM, the format the listener already records. The response is JSON with the text, the language, the segments with their start and end times, the audio's duration and the time taken. The model is named in the server's configuration, not by the caller. **[open]** Streaming partial transcripts. Reason: the listener already cuts an utterance at the end of speech with Silero VAD, so a whole-utterance call is the simplest contract that gives the larger model's accuracy; the NUC's `tiny.en` takes the same input, which keeps the fallback of IS-4 a one-line switch.

9. **IS-9. Routing: `POST /v1/route`; chat: `POST /v1/chat`.**
   - **Route.** The request carries the transcript and the list of agents the NUC can route to, each with its name, description and commands (AG-1, the `[[agents]]` and `[[routes]]` tables). The response names one agent from that list or `none`, with a confidence and any arguments the model read from the transcript. The server never invents an agent outside the list. It is called only by the NUC's rules layer, after the rules have failed to match, so RR-1 holds: no query reaches an agent without a rule deciding it may. **[open]** whether routing by model is wanted at all, or only for what the rules miss.
   - **Chat.** The request carries the agent's name and prompt and the conversation as a list of messages; the response carries the two parts of AG-4, the spoken summary and the detail visual, in the shape the agent asks for, and the tokens used. **[open]** whether the endpoint is OpenAI-compatible (`/v1/chat/completions`), which most local runtimes already serve, with autobot's two-part shape built on the NUC, or autobot's own shape.
   - Both carry no state (IS-5).

   Reason: the owner wants "a local LLM for routing and the core conversational agent". Giving the model a closed list to choose from keeps routing a classification that the rules layer can check, as RR-3 requires each route to name its agent.

10. **IS-10. Model choices fit the 2080 Ti's 11 GB and its Turing architecture.** Every model loaded at once fits, with its working memory, in about 10 GB, leaving room for the roughly 0.3 GB the Windows desktop holds. Turing (compute 7.5) has float16 and int8 but no bfloat16 and no FlashAttention 2, so a runtime that requires either is out. The first candidates, **[open]** until measured on this card:
    - **Speech-to-text:** faster-whisper (CTranslate2) with `large-v3-turbo` or `distil-large-v3` in float16, about 2 to 3 GB. It is the NUC's library already (ADR 0003), so only the model changes.
    - **Language model:** one instruct model of 7 to 9 billion parameters, quantised to about 4 bits (a GGUF `Q4_K_M` is about 5 to 6 GB) with a context of 8 to 16 thousand tokens, served by llama.cpp's server or Ollama, both of which run on Turing. One model serves both routing and chat, so that only one is resident. Which model family is the owner's choice.
    - **Text-to-speech, if it moves here:** a small neural voice of under 1 GB; piper stays on the NUC as the fallback.

    Reason: the card has 11,264 MiB and all three models must stay loaded, because loading one per request would cost seconds a voice reply cannot spare. A 4-bit 8B model and a Whisper large-class model together are the largest pair that fits.

11. **IS-11. `GET /health` says what the server can do.** It answers without touching a model: the server's version, which of `stt`, `route`, `chat` and `tts` are loaded and ready, the model behind each, and the GPU memory used and free. The NUC's health check (IS-4) reads it. Reason: the NUC needs to know not only that the host is up but which jobs it can hand over, since a model can fail to load while the server runs.

12. **IS-12. The server's code lives in this repository, in a `server/` folder, and its tests need no GPU, no model and no network.** The tests drive the endpoints with fakes for the speech model and the language model, as `tests/agents/agent_fakes.py` does for the agents. **[open]** `CONVENTIONS.md` makes `autobot` under `src/` the single package with one `pyproject.toml`; a `server/` folder with its own project definition breaks that, and `autobot.server` under `src/` would not. The owner asked for `server/`; either `CONVENTIONS.md` is amended or the folder is the package. Reason: one repository keeps the client and the server's contract in step, and tests that need a GPU could not run on the NUC, where `make test` runs.

13. **IS-13. Only the NUC can reach the port, and the LAN carries no secret.** The Windows Firewall and the Hyper-V firewall each let TCP in on the server's port from the NUC's address only (`INFRASTRUCTURE.md` lists the rules). The server binds no port on the router's WAN side and is never exposed through the `assistant` project's Cloudflare tunnel. **[open]** Whether a shared token in a request header is added on top of the address filter, and where it would be kept on each host (never in the repository). Reason: audio and transcripts from the house cross the LAN, and the address filter is a rule the owner can read in one line; the house LAN is trusted, but a token would cost little if the owner wants it.

14. **IS-14. The server starts on its own when the PC boots.** A Windows scheduled task starts the WSL distribution at boot and keeps it running; inside WSL a systemd unit starts the server and restarts it when it fails. The NUC does not start, stop or wake the server. Reason: the NUC must be able to rely on the server whenever the PC is up, without the owner opening a terminal on Windows; and the NUC has no rights on the PC, which is the owner's own machine.

## Open Questions

- **Does `CN-1` allow speech-to-text on another machine in the house?** `CN-1` says speech-to-text runs "on the local machine" and forbids "any cloud service, hosted API or remote model". The server is in the house, on the owner's LAN, under his control, and no cloud is involved, but it is not the NUC. `CN-2` says the same of text-to-speech. Recommended: the owner amends `CN-1` and `CN-2` on purpose to say "on the owner's own machines in the house, never a cloud service", with a revision line, before IS-8 is built. Until then IS-8 cannot take effect.
- **Does a local model replace Gemini for the core conversational agent?** AS-1 and ADR 0002 have every agent reason against Gemini in Google Cloud. A local chat model is a change of that decision, or an addition beside it. Recommended: record the owner's choice in a new ADR (0007), saying which agents use which model and whether Gemini remains the fallback when the server is away (IS-4).
- **`server/` or `src/autobot/server/`?** See IS-12. `CONVENTIONS.md` needs amending if the owner keeps `server/`, and the `describes:` of this spec gains `server/**` once the folder exists.
- **Which language model.** Family, size and quantisation are to be chosen by measurement on the card (IS-10): latency to the first token and quality on the routing task.
- **Which runtime.** llama.cpp's server, Ollama, or the model loaded in-process in the server's own Python. The first two bring their own HTTP API; the last keeps one process and one port.
- **Does text-to-speech move here?** piper on the NUC's CPU is already fast for short replies. Moving it gains a richer voice and costs a round trip and the fallback's voice sounding different.
- **Streaming.** Whether STT partials or chat tokens are streamed to the NUC to cut the time to the first spoken word, which needs a WebSocket or server-sent events on the port of IS-2.
- **Authentication.** Address filter alone, or a shared token too (IS-13).
- **Latency budget.** What round trip from end of speech to start of reply counts as good enough to prefer the server over the NUC's own models, and so what the timeouts of IS-4 are.
- **Who registers what on Windows.** The scheduled task, the two firewall rules and the router's reservation are the owner's to make (`INFRASTRUCTURE.md`); the server's plan should list them as its first step, done by hand.
