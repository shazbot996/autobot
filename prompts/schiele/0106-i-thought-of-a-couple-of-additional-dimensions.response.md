# autobot — Agents and the agent tree

autobot's capabilities are **agents**, and the picture of them is the **agent tree**: a top-down flowchart drawn in text, with `autobot` in a box at the root and, under it, one node per agent, joined by the commands that reach them. The tree is shown twice. On the face it fills the detail panel while nothing runs, highlights where the session stands, and moves up the screen as the session goes from wake to command to agent, until the agent's own running view takes the panel over. In the **Agent editor** screen of the configuration menu the same tree is walked with the arrow keys, and Enter opens one agent's full-screen editor, where its name, description and, when it has one, its prompt are read and edited. An agent is autobot's own code: a unit with a definition, a command that reaches it, a screen it drives and, later, state of its own; some wrap a Gemini ADK agent, some answer locally with no AI at all. The first agents after the echo are `question`, `weather` (with its `forecast` alias), `time`, `camera` and `introduce`. Any agent can be set to ask a yes-or-no **confirmation** on the way in and before it sends a request out. A **global action keyword**, `cancel` being the first, leaves whatever runs and goes back one level, unless the agent has turned listening off. The interface gains a **run mode**, the face, and a **configuration mode**, the main menu, and Tab switches between them. Rules AG-1 to AG-15 govern this. The spec builds on the face spec (FS-8, FS-9, FS-10, FS-13, FS-14, FS-15), the rules-first routing stub (RR-1, RR-2, RR-3, RR-4), the agent sessions stub (AS-1, AS-2, AS-4), the studio spec (TS-1, TS-10, TS-11, TS-13) and the Google Cloud configuration screen spec (GC-4, GC-9, GC-10, GC-13). It amends FS-1, FS-9, FS-13 and FS-15 as the "Changes needed elsewhere" section says and withdraws nothing else.

## Numbered rules, each with its reason

1. **AG-1. An agent is a unit of autobot's own code with a definition.** An agent is one capability autobot can be asked for. It has a **definition**, which is data: a `name`, a `description` in a sentence or two, the commands that reach it (the `[[routes]]` rules that name it, FS-15), and, for an agent that calls a language model, the `prompt` that autobot wraps around the owner's words. It has **code**, which the definition does not contain: the experience it runs on the face (FS-10) and whatever it does to answer. An agent that reasons does so through a Gemini ADK agent (AS-1), but the ADK agent is behind autobot's agent, not the agent itself: autobot's code receives the command, builds the request, processes the response in the middle and drives the screen. Every agent is an instance of the same shape, so that the tree, the editor and the router treat them alike. Reason: the owner describes each capability as "a new instance of what we would call an agent" that "could be represented by an ADK agent, but it's more than that": autobot is the code calling the ADK agent and will keep its own state (AG-11). One shape for every agent is what lets the tree and the editor show all of them, whether or not a model stands behind one.

2. **AG-2. The agent tree is a top-down flowchart: autobot at the root, agents as nodes, commands as edges.** The tree has two levels today. The root is a box reading `autobot`, the wake phrase. Under it, joined to it by lines, stand the agents, one box each, drawn in the order of their rules in `config/autobot.toml`. An edge is the command that leads from the root to the agent, and the command's word is written on it, so that the screen always shows the words that will activate each node. Two rules that reach the same agent are **aliases**: they are drawn as two edges into the one node, each labelled with its command and with what differentiates it (AG-7), so the owner sees that they share one logic and how they differ. The tree is drawn in the theme's line-drawing characters where the terminal has them and in plain ASCII where it does not, as the eyes and the banner are (FS-5). It is one model, drawn by both the face (AG-3) and the Agent editor (AG-9), and it lives in a module that does no drawing. Reason: the owner wants an "old-timey ASCII-based flowchart" as the visual cue of what autobot can do, in the way React Flow would show nodes and edges: the nodes are agents, the edges the actions that lead to them. The words on the edges are what makes the picture a hint as well as a map. One model for two screens keeps them from drifting apart.

3. **AG-3. On the face the tree fills the detail panel and follows the session.** While no experience runs, the detail panel shows the tree with the root highlighted in the theme's highlight colour (green where the theme has it): autobot is listening, and the root is the active next step. The tree then follows the session of FS-10 and FS-15:
   - **Wake.** When the listener publishes a wake, the whole chart moves up the screen so that the second level, the agents, stands where the root stood, and the agents' nodes are highlighted with their commands: the hint of what autobot can do now, while it listens for a command.
   - **Command.** When a rule matches, its agent's node is highlighted and the chart moves up again, so that the agent stands at the top.
   - **Running.** Once an agent's node is highlighted, the detail panel expands into that agent's **running view**: the screen the agent designs for itself (FS-9), shown for as long as the experience runs. The tree is not drawn under it.
   - **Done.** When the experience ends, the tree returns, with the root highlighted again.
   - **No command.** When the ten seconds of FS-15 pass without a command, the tree returns in the same way.

   Reason: the owner wants the display to show the current step it is on: the root in listening mode before the wake, the next level highlighted as a hint once the word is heard, and the agent's own screen once one is chosen. Moving the chart up the screen rather than redrawing it from the top keeps the eye on the step that is live. FS-9 already makes the detail panel the agent's; this rule says what it holds when no agent has it.

4. **AG-4. Every response is built in two parts: a spoken summary and a detail visual that fits the panel.** An agent's answer to the owner is one **TTS summary** (FS-8), the text the summary panel shows and autobot reads aloud, written to be easy to hear, and one **detail visual**, the companion that the agent puts in the detail panel, built to fit the panel as it is at that moment, not scrolled into. The agent, not the face, builds both: for an agent that calls a language model, the prompt (AG-1) asks the model for them in a shape autobot's code can take apart, and the code lays the detail out for the panel's size. The prompt and the code around it may be tuned over time; the prompt is edited in the Agent editor (AG-10), the code is not. Reason: the owner interfaces with autobot primarily by voice, and the screen is limited to what fits in the detail view. So every response must be summarised for speech and given a visual that fits, and the owner wants to tweak the prompt wrapped around the query and the logic that constructs the response as the agents mature. Tying a visual cue to every request is, in the owner's words, the most important thing, and part of what makes autobot fun to use.

5. **AG-5. The `question` agent asks a language model and answers.** The command `question` (said as "I have a question" or any sentence containing the word) routes to the first language-model agent. It takes what the owner says after it as the query, wraps it in its prompt, sends it to its Gemini ADK agent (AS-1), and answers with the two parts of AG-4: a spoken summary and a detail visual. It applies no checks and no balances beyond the routing rule that reached it: it is the basic query. The query it sends is text, the listener's local transcript (`CN-1`); no audio leaves the machine. Reason: this is the owner's first large language model agent, "to test a basic query, no checks or balances, to ask a large language model a question and receive a result", and the first exercise of the response shape of AG-4 on a real model. Validation of what is sent is the rules layer's job and comes later (RR-1); the first agent has nothing to validate against.

6. **AG-6. The `weather`, `time`, `camera` and `introduce` agents answer locally, with no language model.** These agents are what a rule can answer without an AI call (RR-2): simple things the owner always asks an assistant for and does not need one for.
   - **`weather`.** Answers with today's weather for a configured location, as a short spoken narrative and a detail visual of the day. The lookup goes to Google's weather API, which needs billing configured on the owner's Google Cloud account and an API key the owner generates. The location is a zip code, and the zip code is the whole of the location setting; the API key is the agent's only other credential. The zip code lives in the agent's definition and is edited in the Agent editor (AG-10). The API key is kept as a secret in Google Cloud Secret Manager, not in the definition, and the owner can edit it in the Agent editor whether or not it is already configured: the editor takes it in a masked field and stores it as a new version in Secret Manager through the service account, by the path of GC-9, and it is written nowhere else. How the secret is set up is defined in the Google Cloud configuration spec (GC-9), not here. The agent also controls its own rate: it limits how often it calls the metered API, and that rate control is written into the agent, with its limit a setting in the agent's definition, edited in the Agent editor (AG-10). The limit defaults to the cap Google Cloud holds on the weather API, 100 lookups a day and 10 a minute (GC-10); the agent's control is the first line, and the cap in Google Cloud is the backstop behind it. The owner expects to use the agent about 50 times a day, so the daily limit is twice his expected use. Its `forecast` alias (AG-7) opens the same agent in forecast mode, which answers with the days ahead instead of today.
   - **`time`.** Says the time, from the NUC's clock.
   - **`camera`.** Also reached by `cameras`. Opens the owner's camera application, which shows his four external cameras in a web browser. That application is a separate program the owner wrote in another project, built with an integration with Home Assistant; autobot does not rebuild it, it invokes it the way the owner does, through that project's `make` targets: `make fourway-server` starts its proxy server, then `make fourway` opens it in Firefox on the NUC's desktop. The owner's copy of that project sits in the `assistant` folder at the root of this project, and the commands run there. The agent runs those two local commands in a row, and they are a setting in the agent's definition, edited in the Agent editor (AG-10), because other agents may run a local command in the same way and the pattern may be shared later. The proxy server runs in the foreground, so the agent starts it without waiting for it to end. The application runs without the Home Assistant server, and autobot does not start Home Assistant. The agent only opens the application: it does not stop the server or close the browser when the owner is done, and a server already running is left running. It is autobot's first act of desktop direction, and it runs on the NUC only: on any other machine it refuses with the one-line message the other NUC-only paths give (TS-11).
   - **`introduce`.** autobot introduces himself: who he is and how he works, in the two parts of AG-4. Its text is a written script in its definition, the same every time, read aloud and edited as a prompt is (AG-10); it is not generated.

   Each has a running view of its own on the face (AG-3) and a spoken summary (AG-4). None opens a connection for reasoning; `weather` fetches its forecast, which is a lookup, not an AI call. Reason: part of the goal is "to find simple tasks that I always use that usually ask an AI agent for that I don't need an AI agent for", trapped by a word and answered at once. These four are the ones the owner named. The camera agent is the experiment he wants in controlling the PC and popping a browser, which the brief names as a secondary goal, and it touches the NUC's desktop, so it belongs under the NUC-only rule. The owner ran `make fourway` from the `assistant` folder with Home Assistant not running, and it worked: Firefox started on the NUC and the prompt returned at once. The owner chose Google's weather service because a Google Cloud account is to be connected to autobot anyway and his personal use fits the free tier. He puts strict rate controls on metered services to avoid charges, and the agent is where this one's control lives.

7. **AG-7. A rule may carry a mode, and two rules to one agent are aliases.** A routing rule (FS-15) names an agent and may also carry a **mode**, a word the agent receives with the command and uses as a parameter. Two rules that name the same agent with different modes, such as `weather` and `forecast`, are aliases of one agent: they run the same code, and the mode is what differs. The tree shows them as two labelled edges into one node (AG-2), and the Agent routing screen lists them as two rules. Reason: the owner wants "a little trick like that to invoke agents to control parameters for simple little things": saying `forecast` opens the weather agent in forecast mode. A mode on the rule gives that without a second agent, and the tree is, in his words, "a perfect use case" for showing the relationship.

8. **AG-8. Tab switches between run mode and configuration mode; the face leaves the menu and the Agent editor takes its place.** The interface has two modes. **Run mode** is the face: autobot in use. **Configuration mode** is the main menu and the screens under it: the studio, the settings, Agent routing and the Agent editor. Tab switches from the main menu to the face. From the face, Tab or Escape returns to the main menu. Tab is a key of the field, not a mode switch, while a text field has the keyboard (as `T` is a letter there, TS-13). The main menu no longer has a **Face** item; its place is taken by **Agent editor** (AG-9), and the menu's numbered entries are the configuration functions. The key bar on both screens shows `Tab` with the mode it leads to. `make launch` always opens on the main menu, in configuration mode, whether or not a model is installed: reaching the face is two steps, open the application and press Tab. Reason: the owner wants the face reached with the Tab key as the main mode of the application, not as a numbered menu item, and the menu kept for configuration, with the Agent editor as its new screen. Opening on the main menu follows FS-1, which chose the menu as the opening screen, and the owner confirmed it should stay so.

9. **AG-9. The Agent editor screen is the tree, walked with the arrow keys.** The **Agent editor** is a screen of the configuration menu that draws the same tree as the face does (AG-2), with the same graphics, and a selection on one node. Up and Down move the selection a level, Left and Right move it between the nodes of a level, and Enter opens the selected agent's editor view (AG-10). On the root node Enter does nothing beyond saying that the root is the wake phrase, which the Wake phrase screen edits. Reason: the owner wants the editor "to look just like the flowchart that we're going to display in the face app", moved through with the arrow keys as a tree that has two levels for now.

10. **AG-10. The agent editor view shows how an agent is built and edits its definition, not its code.** Enter on an agent opens a full-screen view of that agent. It shows the definition of AG-1: the name, the description, the commands and modes that reach it, whether a language model stands behind it, and, for an agent that has one, the prompt in a multi-line text field. It also says what the agent's code does, as text, so that the owner can see how the agent is built; the owner pre-programs that description, since most of an agent is hard-coded procedural logic. The name, the description, the prompt and an agent's own settings, such as the weather agent's zip code and rate limit and the camera agent's local commands, are edited here by typing; every edit is written at once to the agent's `[[agents]]` table in `config/autobot.toml`, whose multi-line strings carry long prompts (TS-10). The weather agent's API key is the exception: it is a secret kept in Google Cloud Secret Manager (AG-6), not in that table, and it is pasted into a masked field and stored as GC-9 says. The commands that reach an agent are shown here and edited on the Agent routing screen, which writes the same `[[routes]]` rules. The Agent routing screen stays a separate screen of the configuration menu: it is where commands are edited, and it also tries a typed sentence against the rules, which the editor does not. The view does not edit code: an agent's experience and the logic around its prompt are changed in the repository. Reason: the owner wants a place in the configuration application "to see and edit at least the metadata for the agents we have configured so far", and in particular the prompt, since "we usually will wrap our queries around a prompt to give it the context we need", while being clear that "this interface is not intended to edit the code that an agent is running". The layout convention admits no second store, and TOML carries multi-line text.

11. **AG-11. Agents keep their state on this machine, in this layer.** When an agent keeps state between sessions, the state lives on the NUC (AS-2, ADR 0002), is owned by autobot's agent code of AG-1 rather than by the ADK agent behind it, and is kept beside the agent's definition once a shape for it is fixed. No agent of this spec keeps state yet; this rule names where it goes when one does. The persisted data is also meant to serve as the retrieval layer the agents draw on. Reason: the owner says "right now, we're not keeping state, but we're going to, this is the layer when we do where we will, because we're going to be processing all of the responses in the middle". Saying so now stops the first stateful agent from putting its state somewhere else.

12. **AG-12. Speech stays local, only text leaves, and the logic is testable without a terminal.**
    - **Speech.** Every agent hears through the listener's local transcripts and speaks through the face's local piper voice (FS-13, `CN-1`, `CN-2`). No agent sends audio anywhere.
    - **Network.** The face opens a network connection only on an agent's behalf: the `question` agent's reasoning, as text, to Gemini in the owner's Google Cloud project (AS-1), the `weather` agent's lookup to Google's weather API, and the read of the weather API key from Google Cloud Secret Manager, all as the service account (GC-4). The echo, `time`, `camera` and `introduce` open none. In configuration mode the only connections are the Google Cloud screen's checks and the storing of a pasted secret (GC-13), which includes the weather API key edited in the Agent editor (GC-9).
    - **Testable.** The tree model, the agents' response shaping (AG-4), the mode handling (AG-7) and the editor's logic live in modules that do no drawing and are tested with fakes for the model, the lookup and the browser launch, with no microphone, speaker or network (FS-14).
    - **Secrets.** The credentials the `question` agent needs and the weather API key are not in the repository and not in `config/autobot.toml`; a missing credential is a one-line reason in the summary panel with the *trouble* reaction, not a traceback.

    Reason: `CN-1` and `CN-2` forbid any cloud speech path, and ADR 0002 has the agents reason in the cloud with everything else local. FS-13 says the face opens no network connection, written when the echo was the only agent; the first agent that reasons needs the one exception, and naming it keeps the rest closed. `CONVENTIONS.md` "Testing" and "Control layers" require the logic to be testable without a terminal and failures to be one line. `AGENTS.md` keeps the Google Cloud credentials out of the repository.

13. **AG-13. Any agent can ask a yes-or-no confirmation on the way in and before it sends a request out.** A **confirmation** is one shape, the same for every agent, and every agent's definition carries two of them, each turned on or off independently in the Agent editor (AG-10):
    - **On the way in.** After the command matches and before the agent's experience starts.
    - **Before a request goes out.** Before the agent sends a request off the machine, such as the `weather` agent's lookup or the `question` agent's call to its language model. Only an agent that sends a request offers this one.

    Each confirmation has a yes-or-no question, text in the agent's definition that the owner edits in the Agent editor, for example "This may cost a few dollars. Are you sure you want to run this?". When a confirmation is on, autobot reads the question aloud in the local voice and shows it (AG-4, AG-12), then listens for the answer in the listener's local transcripts. The answer is permissive: any word of a long list counts as yes, such as "yes", "affirmative", "okay" and "go ahead". A yes continues. A no, `cancel` (AG-14), or ten seconds without a yes (the wait of FS-15) stops the agent and returns the session one level, as `cancel` does. Words that are neither yes nor no count for nothing. Both confirmations are off by default, so an agent with neither on launches at once, as the echo does now. The confirmation logic and the matching of answers live in modules that do no drawing and are tested as AG-12 says. Reason: the owner wants a guard on an agent that "as soon as we say the word, launches into a thing", and a second one before a request that may cost money, which he puts "on with a large language model process that may cost a little bit of money". Making it one setting that every agent has, rather than code in each agent, follows AG-1, where every agent has the same shape.

14. **AG-14. `cancel` is a global action keyword: it leaves whatever runs and goes back one level.** A **global action keyword** is a word that means the same thing at every step of a session and in every agent. It is checked before the routing rules (FS-15) and before an agent's own handling of what it hears. `cancel` is the first of what will be a growing list. While the face is listening during a session and hears `cancel`, it stops whatever process is running and goes back to the previous level of the tree (AG-3):
    - from an agent's running view, or from one of its confirmations (AG-13), to the agents' level, listening for a command as after a wake, with the ten seconds of FS-15 starting again;
    - from the agents' level to the root.

    At the root no session runs, and `cancel` is an ordinary word. While the face speaks the listener holds its ears, so `cancel` is heard between autobot's utterances, not over them. An agent that has turned listening off (AG-15) does not hear it. Reason: the owner wants "a global action keyword" that, said "while the mic is in listening mode", will "exit whatever process it's in and go back to the previous level". One level at a time matches the tree, which moves down one level at each step of the session.

15. **AG-15. An agent can turn listening off for its running view.** An agent's definition has a listening setting, on by default and edited in the Agent editor (AG-10). When it is off, the face does not listen while that agent's running view is shown, and no global action keyword (AG-14) reaches it; the agent controls its flow, and when it ends, some other way. A confirmation the agent has turned on (AG-13) still listens, since it needs an answer. Reason: the owner expects "use cases where we are going to have to control that flow some other way", and an agent that needs that must be able to stop `cancel` from cutting it short.

## Settled without asking

- **Default.** Both confirmations are off by default, so every agent keeps launching at once, as the echo does today (AG-13).
- **Default.** Only a yes continues past a confirmation. A no, `cancel` or ten seconds of silence stops the agent, and other words count for nothing, because a confirmation guards cost (AG-13).
- **Resolved.** The confirmation before a request goes out is offered only by agents that send one, since it has nothing to guard in the others (AG-13).
- **Resolved.** After `cancel` takes the session back to the agents' level, the ten seconds of FS-15 start again, as after a wake (AG-14).
- **Resolved.** Turning listening off covers the agent's running view only; its confirmations still listen for their answer (AG-15).
- **Resolved.** The face holds the listener's ears while it speaks, so `cancel` cannot be heard over autobot's own speech (AG-14).

## Open Questions

- **Confirmations in the tree.** The owner calls confirmations "conditionals that … also act like agents", but nothing says how the tree shows them. Recommended default: a mark on the agent's node, on the face and in the Agent editor, rather than a node of their own, so that the tree keeps its two levels of commands and agents.
- **Where the word lists and global keywords live.** The list of words that count as yes, the words that count as no, and the global action keywords all need a home. Recommended default: one shared list of each in `config/autobot.toml`, not one list per agent, because the layout convention admits no second store and the words mean the same thing for every agent.
