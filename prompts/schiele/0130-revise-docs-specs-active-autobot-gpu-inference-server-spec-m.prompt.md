The goal, in the owner's words: a robust, fast and fun local model layer on GAMEON1 that serves the NUC, hands hard requests to the upstream Gemini ADK agents, and is programmable and extensible in its own right, so new agents and tools are added without rewriting the server.

Answers to the open questions
CN-1 / CN-2. The owner amends both, on purpose: speech-to-text and text-to-speech run on the owner's own machines on the house LAN (the NUC and GAMEON1), never on a cloud service, hosted API or remote model outside the house. Wake-word detection and modelling stay on the NUC only. IS-8 takes effect once CONSTRAINTS.md carries the amendment; list it under Changes needed elsewhere, with the AGENTS.md sentence "a change to the listener's speech path keeps it offline", which becomes "keeps it inside the house and off any cloud".
Local model vs Gemini. An addition beside Gemini, not a replacement. Record it as a new ADR 0007 (Changes needed elsewhere). Each agent definition names its model: none, local or gemini, and an ordered fallback. AS-1 stays true for every agent whose model is gemini.
Layout. server/ at the repository root, with its own pyproject.toml and its own package autobot_server under server/src/, tests under server/tests/. Reason: the server has GPU dependencies the NUC must never install. CONVENTIONS.md is amended to "one package per host". make lint and make typecheck cover server/ too.
Language model. One instruct model of 7 to 9 billion parameters at about 4 bits, serving routing, slot filling and chat, chosen by measurement, not named in the spec. The model is a value in config/autobot.toml; changing it needs no code change. Candidates to measure first: a Qwen3 8B, a Gemma 4 that fits, and Llama 3.1 8B, each at Q4_K_M.
Runtime. Ollama on GAMEON1, bound to 127.0.0.1 only, behind autobot's own server on port 8300, which is the only thing the NUC talks to. The server reaches the runtime through one seam, so llama.cpp's llama-server can replace Ollama without a contract change. The server never pulls a model: a missing model is a one-line "not ready" in /health; models arrive only through make server-fetch-models.
Text-to-speech. Not in the first version. piper on the NUC stays the voice. /v1/tts is reserved and /health reports tts: false. A later revision may add a neural voice (for example Kokoro) with piper as the fallback.
Streaming. Speech-to-text is not streamed: utterances are short and cut by the NUC's VAD. Chat may stream tokens as server-sent events on the same port (stream: true), so the NUC can speak sentence by sentence through piper. Routing never streams. No WebSocket.
Authentication. Address filter plus a shared bearer token. The token lives outside the repository on each host (on the NUC under the git-ignored secrets/, on GAMEON1 under ~/.config/autobot-server/), mode 0600, created by the owner with a make target the owner runs; agents never read or print it. A request without the right token gets 401. A missing token on the NUC is a one-line reason and the server counts as down. Reason: the Hyper-V firewall and host-policy merge are untested and Windows classes the LAN as Public, so the token makes a firewall mistake fail closed.
Latency budget, measured from the end of speech:
a keyword-routed local answer starts speaking within 1.0 s;
a server-transcribed, server-routed command reaches its agent within 1.5 s;
a local chat reply starts speaking within 2.0 s (streamed);
a Gemini handoff shows a visible "thinking" cue within 0.5 s. Timeouts: health 1.0 s; speech-to-text 0.5 s plus 0.25 s per second of audio; route 1.5 s; chat 3 s to first token and 30 s total. On a timeout the NUC falls back at once and does not retry that request.
Windows and router steps. The plan's first step, done by hand by the owner, lists: the DHCP reservation, both firewall rules, the start-up task, the apt install of python3.12-venv, python3-pip, make and nodejs, the Ollama install, and lingering for the server's user unit. This host is the owner's gaming PC, so the server must expect to lose the GPU (see IS-24).
Amend these rules in place
IS-1: the NUC is the only remote client; GAMEON1 may call its own server on loopback for make server-check.
IS-4: replace the fixed fallback list with the per-job fallback of IS-23 and the agent fallbacks of IS-18.
IS-8: the request also carries the vocabulary hints of IS-16, and the response says which model transcribed it.
IS-9: the route request carries each agent's modes and parameter schema; the response's agent and mode are constrained by a JSON schema enum built from that list (plus none), not only checked afterwards. Chat uses autobot's own shape, not /v1/chat/completions: the NUC sends the system prompt, the messages, an optional response_schema (the AG-4 two-part shape) and optional tools (IS-21). The two parts are taken apart on the NUC, by the agent (AG-4).
IS-10: replace the loose figures with a VRAM budget that the server checks at start and reports in /health: speech-to-text at most 3 GB (faster-whisper large-v3-turbo, int8_float16 or float16, whichever measures better on Turing); language model weights about 5 GB plus a KV cache of at most 1.5 GB (8k context by default, one parallel slot, a quantised KV cache where the runtime offers it); about 1 GB for CUDA contexts; total at most 10.5 GB of the 11,264 MiB with the desktop's ~0.3 GB taken. Mention that faster-whisper's own README measures large-v2 at 4,525 MB in fp16 and 2,926 MB in int8 (beam 5, RTX 3070 Ti), so the turbo figure is to be measured, and that current CTranslate2 needs CUDA 12 cuBLAS and cuDNN 9, which can come from pip wheels without a CUDA toolkit.
IS-12: tests need no GPU, model or network; the request and response examples live once under server/contract/ and both the NUC's and the server's test suites check against them.
New rules
IS-15. The wake path never touches the server. Wake detection, by every engine including text_match, stays on the NUC and never waits on the network. The server transcribes only utterances inside a session after a wake: the command, the query, confirmation answers. Every transcript says whether it came from the server or from the NUC's tiny.en. Reason: CN-1 keeps wake detection local, and IS-4 says a wake is never lost.
IS-16. Vocabulary biasing. Each speech-to-text request carries hints built on the NUC from the agent names, their commands, modes and aliases, the yes and no words and the global action keywords, capped in length, which the server passes to the model as hotwords or an initial prompt. Reason: transcription is the owner's weakest link today, and these words are what routing depends on.
IS-17. Routing is a cascade inside the rules layer. Global action keywords first (AG-14). Tier 1: the [[routes]] keyword rules as today (FS-15). Tier 2: a semantic match on the NUC's CPU with a small local embedding model against each route's command and example phrases, above a configured threshold. Tier 3: the server's language model, constrained to the closed list (IS-9). The rules layer admits a tier's answer only if the agent exists, the mode is one of its modes, the parameters validate against its schema, and the confidence passes that tier's threshold; then AG-13's confirmations apply as for any route. When nothing is admitted, the core agent (IS-19) takes it if the server is up, otherwise autobot says it did not catch that. The tier that decided is shown on the face (the edge on the map can mark it). With the server away, tiers 1 and 2 still work. Reason: RR-1 holds because a rule still admits every route; the NUC keeps most of its routing when GAMEON1 is off; and the cheapest tier answers first. (Tier 2 on the NUC differs from the chat's sketch, where every model was on the server; flag it as settled without asking.)
IS-18. Agents come in tiers. An agent definition gains model (none, local, gemini), fallback (an ordered list of the same, or a spoken line), and parameters (named slots with type, allowed values and whether required). A none agent runs code only; a local agent with parameters gets them filled by the route call; a local or gemini agent that reasons calls its model through the existing model seam (autobot.agents.gemini.Model), of which the local model is a second implementation. The definitions are data in [[agents]], edited in the Agent editor.
IS-19. The core agent. A new agent, core, whose model is local, is autobot's conversational self. Its personality is its system prompt, in its definition, edited in the Agent editor. It is the default when no route is admitted (IS-17). It is multi-turn within a session (AS-5): the conversation is kept on the NUC (AG-11), sent whole with each request (IS-5) and trimmed to the context budget by dropping the oldest turns. When the server is away it follows its fallback.
IS-20. Handoff to Gemini. The core agent's structured answer may ask to hand the request to one upstream Gemini agent from a closed list it is given, with the query it should get. The NUC carries out the handoff, as the service account (GC-4), after AG-13's before-request confirmation if that agent has it on, and within GC-10's caps. The server never calls a cloud service (IS-7).
IS-21. Tools without server changes. Tools are declared in the NUC's agent definitions and sent with each chat request as schemas. The model may answer with tool calls; the NUC runs them and sends the results in the next request, at most a configured number of rounds per turn. The server executes no tool and holds no agent list, so adding an agent or a tool changes only the NUC's configuration and code. Reason: extensibility without touching the server, and IS-5 statelessness.
IS-22. The contract is versioned. Endpoints sit under /v1, and /health reports the contract version. A NUC that finds a different major version treats the server as down, with a one-line reason on the main screen. Reason: the two hosts are updated separately, by a pull on each.
IS-23. The NUC watches for the server. States: unknown, up, degraded (some jobs ready), down. It polls /health every 5 s while up and backs off from 5 s to 60 s while down; two failures in a row mark it down, one healthy answer marks it up. Each job falls back on its own. The main screen shows the state beside the listener's, and the face reacts when the server comes or goes. The server reports a job ready only after its model has loaded and answered one warm-up request. Reason: the owner wants the NUC to "look for the API to come alive", and a model can fail while the process runs.
IS-24. The GPU can be taken away. Every resident model loads at start and stays loaded. A job that hits a CUDA out-of-memory error, or loses the GPU to a game, reports not ready rather than crashing or restarting in a loop, and recovers when memory frees. A busy job holds at most one waiting request and answers any further one at once with 503 and Retry-After, so the NUC falls back instead of waiting.
IS-25. Runtime control on GAMEON1 is make. server-setup, server-fetch-models (the only downloader on that host), server-up, server-down, server-status, server-logs, server-install (a systemd user unit with lingering) and server-check (a loopback smoke test of each endpoint with a committed fixture). The server refuses to start unless the hostname equals the configured server hostname, as TS-11 does for the NUC. On the NUC, make server-ping checks the server from the NUC. All appear in the bare make summary.
IS-26. Evaluation, not tests. make server-eval runs on GAMEON1 against the real models: route accuracy on a committed, labelled set of typed utterances (no owner audio, TS-5), JSON validity against the schema, and latency to first token and to full answer, written to a report file. It is how the language model of IS-10 is chosen.
IS-27. Audio-native models are out of the first version. Qwen2.5-Omni-3B's own README gives a theoretical minimum of 18.38 GB in BF16 (15 s of video), and Turing has no bfloat16, so it cannot be resident beside the others on 11 GB. It may be tried later as an experiment profile, off by default, that unloads the other models and returns text only.
